# 일일 개발 작업 절차

[제품 방향](../../ROADMAP.md)과 [일일 카드](daily-cards.md)를 함께 읽는다. 한 번에 카드 하나만 진행한다. 날짜와 카드 번호는 고정 대응하지 않는다.

## 시작과 선택

1. 현재 브랜치·작업 폴더·원격 차이·최근 CI를 확인한다. 기존 변경은 보존한다.
2. `IN_PROGRESS` 또는 실패한 `VERIFYING` 작업이 있으면 우선 마무리한다.
3. 없으면 ROADMAP의 현재 우선 대기열에서 선행 작업이 끝난 첫 카드를 고른다. 대기열 이후에는 남은 `READY`/`PLANNED` 카드의 번호순이다. `WAITING_OWNER` 작업에 의존하지 않는 다음 준비된 카드를 선택할 수 있다.
4. 사용자 문제, 변경 범위, 재현 입력, 기대 결과를 먼저 정한다. 구현·로컬 검증 60~90분 안에 끝내기 어려우면 독립적인 하위 카드로 나눈다.
5. 기초 컴포넌트를 만드는 날은 그 계약과 테스트를 완료한다. 연결되지 않은 UI를 노출하거나 전체 기능을 출시했다고 표시하지 않는다.

상태는 `PLANNED → READY → IN_PROGRESS → VERIFYING → DONE`이다. 외부 피드백·권한·환경이 필요하면 `WAITING_OWNER`, 해결되지 않은 재현 가능한 실패는 `BLOCKED`로 이유를 적는다. 상태 변경은 작업 근거와 함께 기록한다.

## 공통 검증 프로필

카드의 검증 항목은 아래 프로필에 추가하는 시나리오다. 외부 DB 검사를 문서 검사로 대체하지 않는다.

**C — 코드 기본**

```powershell
npm run compile-tests
npm run compile
npm run test:unit
```

타입·린트·번들과 단위 검사다. 새 테스트는 실제 결함과 경계를 확인한다. 구현과 똑같은 로직을 다시 쓰는 테스트는 추가하지 않는다.

**H — Extension Host/UI**

```powershell
npm run test:extension
```

활성화·명령·VS Code API를 검증한다. 실제 DOM을 다루지 않는 자동 검사만으로 클릭·포커스·테마를 검증했다고 쓰지 않는다. 카드에 적힌 UI 동작을 수행하고 화면/응답을 남긴다. 화면 확인이 불가능하면 그 부분은 미확인으로 남긴다.

**D — 실제 DB**

```powershell
docker compose -p dbunny-verify up -d --wait --wait-timeout 180
npm run test:integration
```

이 프로젝트의 테스트 계정·전용 포트만 사용한다. 개발 중 관련 파일을 직접 실행해 재현할 수 있지만 최종 DB 경로 변경은 전체 통합 runner를 통과해야 한다. 포트·격리는 [개발 가이드](../../CONTRIBUTING.md)를 따른다. 데이터를 공유하는 현재 통합 묶음은 병렬 실행하지 않는다.

**P — 실제 VSIX**

```powershell
npm run package-extension -- --out dbunny.vsix
$env:VSCODE_TEST_VERSIONS = '["1.85.0","stable"]'
npm run test:package -- dbunny.vsix
Remove-Item Env:VSCODE_TEST_VERSIONS
```

패키지·의존성·배포 설정을 바꾸면 수행한다. 배포 후보는 [CI](../CI.md)의 모든 OS/버전 및 태그·패키지 일치 검사도 필요하다. 일반 UI 카드마다 같은 전체 호환 검사를 수동 반복하지 않는다.

**W — 문서/자료**

참조한 경로·명령·내부 링크와 출시 버전을 확인한다. 화면은 테스트 데이터로 촬영하고 개인정보·실제 호스트·비밀번호를 제외한다. 문서만 바뀌면 불필요한 DB 전체 검사를 반복하지 않는다. 기능 코드가 함께 바뀌면 C/H/D/P 중 필요한 검사를 더한다.

## 검토, 커밋, 원격 확인

- diff에 관련 변경·테스트·설명만 남긴다. 개인 설정·비밀값·DB·로그·VSIX·캐시·빌드 산출물을 stage하지 않는다.
- 관리자의 author/committer를 확인하고 목적과 실제 변경을 한글 커밋 메시지로 설명한다.
- 원격을 확인한 뒤 현재 브랜치에 정상 push한다. 강제 push·공개 태그 교체를 하지 않는다.
- 원격 SHA와 CI 결론을 확인한다. 실패하면 같은 기능 범위에서 수정한다.
- 구현 SHA·검증 명령·CI URL·제약을 기록한 뒤 완료를 판정한다. 실행 중인 CI는 `VERIFYING`이다.
- 커밋은 자기 자신의 해시를 담을 수 없다. 구현 SHA의 카드 연결은 다음 관련 변경이나 실제 검증 내용을 담는 후속 기록에 반영한다. 날짜별 빈 기록 파일은 미리 만들지 않는다.

## 완료 기록 형식

작업한 카드 아래에 추가한다. 로그 원문은 `test-results/`에 두고 공개 기록에는 필요한 요약만 남긴다.

```text
실행일: YYYY-MM-DD
상태: DONE 또는 VERIFYING/WAITING_OWNER/BLOCKED
구현: commit URL
재현: 입력 → 변경 전 결과 → 변경 후 결과
검증: 명령/환경/통과 및 실패 범위
CI: run URL과 결론
사용자 변화: 지금 할 수 있게 된 행동 한 문장
제약/다음 범위: 미확인 사항과 분리한 작업
```

매일 릴리스 태그를 만들지 않는다. 배포 후보 카드는 검증·노트를 준비하며 Marketplace 게시는 승인한 버전과 범위에서만 수행한다. 외부 홍보는 초안과 데모를 준비하고 게시 대상·시점은 별도로 정한다.
