# 작은 일일 작업 절차

매일 [NEXT.md](NEXT.md) 하나에서 시작한다. [전체 카드](daily-cards.md)는 120개 부모 기능의 참고 자료이고, 실행 단위는 **304개 하위 작업**이다. [work-items.json](work-items.json)은 ID·의존성·순서·작은 목표를 찾는 목록이다.

예를 들어 다음 항목이 필요할 때만 아래처럼 하나를 골라 읽는다. 전체 목록을 출력하지 않는다.

```powershell
node -e "const w=require('./docs/roadmap/work-items.json'); console.log(w.parents.flatMap(p=>p.units).find(u=>u.id==='D001-2'))"
```

## 하루 범위와 읽는 양

- 개발·로컬 확인 20~30분, 주 코드 파일 1개와 관련 테스트가 기본이다. 한 함수·한 상태 전이·한 오류 경계처럼 독립적으로 검증할 수 있는 변화 하나만 만든다.
- NEXT와 로컬 작업 규칙을 먼저 읽고 관련 심볼을 검색한다. 처음 소스는 1~2개 파일의 필요한 부분, 합계 약 200줄 안에서 시작한다. 이해에 필요한 경우만 넓힌다.
- 전체 ROADMAP·전체 카드·전체 JSON·과거 대화를 매번 다시 읽지 않는다. 최신 문서도 오늘 바꾸는 API에 필요한 부분만 확인한다.
- 전역 리팩터링·여러 DB·다른 카드로 범위를 확장하지 않는다. 환경이 없거나 예상보다 크면 원인과 더 작은 다음 범위를 남기고 그날은 멈춘다.
- 테스트 없는 구현을 다음 날로 넘기지 않는다. 기초 컴포넌트도 자기 계약과 실패 경계를 검사한 정상 상태로 끝낸다. 대기 중인 UI까지 출시했다고 표시하지 않는다.

## 검증과 출력

프로필의 실제 명령은 [개발 가이드](../../CONTRIBUTING.md)에 있다.

- C: 타입·린트·변경에 맞는 단위 검사. 동일 내용의 검사를 로컬에서 반복하지 않는다.
- H: 활성화·명령·Host/UI 경로를 바꿀 때 Host 검사와 필요한 실제 UI 행동. DOM을 보지 않은 Host 검사만으로 시각 검증을 주장하지 않는다.
- D: DB 실행 경로를 바꾸면 전용 Docker DB의 실제 통합 검사. 단순 타입·문서 변경에 DB를 새로 띄우지 않는다.
- P: 패키지·의존성·배포 설정을 바꾸면 VSIX·최소/stable, 릴리스 후보는 전체 호환성 검사. 일반 카드마다 VSIX를 다시 만들지 않는다.
- W: 문서만 바꾸면 링크·명령·출시 범위 확인. 소스 타입·DB·VSIX를 불필요하게 반복 실행하지 않는다.
- 부모 카드의 검증은 전체 기능이 연결됐을 때의 기준이다. 각 하위 작업은 오늘 바뀐 경계에 필요한 검사를 함께 수행하며 필수 검사를 생략하지 않는다.
- 테스트 stdout/stderr는 `test-results/`로 보관한다. 통과 시 명령·종료 코드·건수만 출력하고 실패 시 해당 검사와 마지막 40~80줄만 읽는다. 전체 로그는 필요한 경우만 확인한다.

## 전달과 다음 작업

1. 시작 때 작업 폴더·브랜치·원격과 직전 CI를 한 번 확인한다. 기존 변경을 보존하고 실패한 필수 CI가 있으면 새 카드 대신 그 실패만 처리한다.
2. 로컬 필수 검증이 통과하면 관련 변경과 NEXT를 함께 커밋·push한다. 한글 메시지/본문에 하위 ID를 넣고 저장소 관리자의 author·committer를 확인한다.
3. NEXT는 다음 하위 ID와 작은 목표·시작 위치·검증·선행 조건만 담는다. 직전 작업은 `VERIFYING`으로 남기고 push된 CI의 실제 성공이 완료 근거다.
4. CI는 상태 요약을 30~60초 간격으로 확인한다. 실패한 step의 로그만 읽고 수정한다. 다음 실행에서 확인한 직전 결과는 다음 실제 변경과 함께 반영한다.
5. 최종 보고는 사용자 변화·실제 검사·커밋/CI·다음 ID를 5줄 안팎으로 적는다. 상태만 바꾸는 커밋·빈 커밋·날짜별 빈 기록은 만들지 않는다.

완료 순서는 부모 우선순위 D001 → D108 → D008 → D105 → D115, 이후 남은 부모 번호순이다. 부모의 하위 작업은 순서대로 진행하고 다른 부모 의존성이 끝나지 않았으면 시작하지 않는다. 부모의 마지막 작업에서 통합된 완료 기준을 확인한다.

오류와 필수 검증에 따라 시간이 달라질 수 있다. 같은 날 두 번째 작업을 시작하지 않고 목표가 크면 독립적인 후속 작업으로 분리한다.

릴리스 태그·Marketplace 게시·외부 홍보 전송은 일반 일일 개발과 별도다. 기존의 승인 범위와 [게시 절차](../PUBLISHING.md)를 따른다.
